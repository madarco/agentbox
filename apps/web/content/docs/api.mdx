title: REST API
description: A versioned HTTP API for launching and managing boxes — for IDEs, scripts, and remote hubs
---

The hub serves a small, versioned **REST API** under `/api/v1` on the same port as
the [hub UI](/docs/hub) and relay (`http://127.0.0.1:8787` locally). It's for
programmatic callers — IDE integrations, scripts, macOS apps, etc. — and is the
way to drive AgentBox when the hub runs on a **separate host** (a control
plane), where there's no local CLI to shell out to.

This is not a second surface bolted onto the side. The AgentBox **CLI itself** drives every box and fleet operation through this same `/api/v1` — create, lifecycle, listing, git, approvals, services, checkpoints, prune and custody all go through the hub, against a local hub and a remote control box alike. "Enable a remote hub" is a base-URL swap, not a different code path. (The one operation still handled outside the API is the **direct IO plane** — `shell`, `attach`, `cp`, `download`, `code`, `open` — which talks to the box from your machine; see [what still needs your laptop](/docs/deployed-hub#what-still-needs-your-laptop). `url` and `screen` go through the API on every provider, except `--loopback`, which by definition means "this machine".)

<Callout type="info" title="Local vs. remote">On your own machine you can also just call the CLI with `--json` (`agentbox list --json`, `agentbox status <box> --json`). The API is what you reach for across a network, or when you want one stable HTTP contract instead of spawning a process per call.</Callout>

## Base URL and versioning

```
http://127.0.0.1:8787/api/v1
```

Every path is prefixed with `/api/v1`. The version is in the path so future
breaking changes can ship as `/api/v2` without disturbing existing clients.

## Auth

Every endpoint except `/health`, `/openapi.json`, and `/docs` requires the hub
token as a **Bearer** credential:

```bash
TOKEN=$(cat ~/.agentbox/hub/token)
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8787/api/v1/boxes
```

The token is the same per-machine secret the hub prints on boot (and stores at
`~/.agentbox/hub/token`, mode `0600`). Requests without a valid token get a JSON
`401` — never a redirect, so non-browser clients work cleanly.

On a **deployed control box** (password-protected hub), `/api/v1` accepts either
the logged-in browser session **or** a headless **API key** as the same
`Authorization: Bearer` credential — so the CLI, the menu-bar app, or a script can
call the remote hub without a cookie:

```bash
# the key is minted + recorded by `agentbox hub setup`/deploy
KEY=$(grep '^AGENTBOX_HUB_API_KEY=' ~/.agentbox/control-plane/control-plane.env | cut -d= -f2)
curl -H "Authorization: Bearer $KEY" https://<your-control-box>/api/v1/boxes
```

The key (`AGENTBOX_HUB_API_KEY`) gates only `/api/v1`, never the UI pages (those
still require a login). A wrong or missing key gets the same JSON `401`.

## Response shape

Success responses return the resource or collection directly. Errors are always:

```json
{ "error": { "code": "not_found", "message": "box not found: abc123" } }
```

with an HTTP status that matches the `code` (`400 invalid_request`,
`401 unauthorized`, `404 not_found`, `409 conflict`, `503 backend_unavailable`,
`500 internal`).

Two more codes also answer `409`, and both carry a `details` object naming the
machine the call has to run on: **`wrong_host`** (a manager op sent to a hub that
is not the machine running the session) and **`manager_unreachable`** (a message
the answering hub cannot type). Branch on `error.code`, not on the status:

```json
{
  "error": {
    "code": "wrong_host",
    "message": "manager 4f2a…c1 runs on marcos-mbp, not on control-box; resume it there",
    "details": { "host": "marcos-mbp" }
  }
}
```

When `details.host` is your own hostname, retry the identical call against the
hub on your machine (`agentbox hub target --json --local`). A refusal about a
**workspace** rather than one manager — `managers/start`, `managers/sessions` —
also carries `details.hosts`, every machine with a checkout of it, because a
workspace mapped from several machines has no single right answer; retry when
your hostname is in that list.

### Checkpoints

Checkpoints are **durable per-project assets** — a docker image or cloud snapshot the box's create warms from. They outlive the box and live in a store on the hub's machine, keyed by the absolute project root (so on a genuinely remote control box a thin laptop can't list them by its own path — a limitation of path-hash-keyed stores). `agentbox prune` never touches them.

Optional body `{ name?, merged?, setDefault?, replace? }`. Returns `{ ok, name, kind, ref, provider, dir?, setDefaultKey? }`. Backs `agentbox checkpoint create`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

### Workspaces

A workspace groups one or more projects, owning a task list and its manager sessions. It is
**machine-independent**: `projects` are repos, and `hosts` maps every machine that has a checkout to
its folders (`{ "<hostname>": { root, projectRoots, seenAt } }`), so a hub that never cloned a repo —
a control box — still joins the boxes built from it to the right workspace. `root` on the payload is
the _reading hub's_ own folder and is absent when it has none. You rarely register one by hand:
detecting a manager session in a folder no workspace contains creates one there. Host state: a
hosted hub holds none, so its listing is empty rather than an error.

The **client scans**, the hub records: the folders are on the caller's machine and the hub never
stats them.

| Method + path                  | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /workspaces`              | Registered workspaces: `{ workspaces: [{ id, name, projects, hosts, root?, projectIds, taskCounts, managers }] }`. A project is `{ id, name, repoUrl? }`, keyed by its normalised origin (or by `<host>:<folder>` with no remote). `projectIds` carries those ids **plus** the path hash of each folder this hub has, which is what a box record and `GET /projects` key by. `managers` is `{ running, total }`.                                                                                                                                                                                                                                                                                                                                              |
| `POST /workspaces`             | Register `{ host, root, projects: [{ path, name?, repoUrl? }], name?, id? }` — the scan the caller ran on **its own** machine (the folder itself and its immediate subfolders with a `.git` or `agentbox.yaml`, each with its `origin`). Idempotent, matched in order by `id`, then by (`host`, `root`), then by any shared repo in a record that has no folder on `host` yet — that last case merges another machine's checkout into the existing record instead of forking a rival workspace, while a second working copy on the same machine stays its own workspace. Project folders on the **hub's own** machine are registered in `GET /projects` too; another machine's are not the hub's to register. `agentbox workspace rescan` re-posts with `id`. |
| `GET /workspaces/{id}`         | One workspace.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `POST /workspaces/{id}/rename` | `{ name }`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `DELETE /workspaces/{id}`      | Unregister it and drop its tasks and managers. The folder, its projects and their boxes are untouched. `409` while any of its managers is running, unless `?force=1`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

`GET /projects` gains `workspaceId` on every project a workspace lists, and `GET /boxes` gains
`tasks` (`{ total, done, current }`) on every box tasks are assigned to and `managerId` on every box a
manager session created. All are optional: absent means "no data" — never "zero" — and all are
absent on a hosted hub. A box created from the web UI or the tray has no `managerId`.
`GET /boxes` also gains `pr` (`{ repo, number, url?, state }`, `state` one of `open`, `ready`, `merged`,
`closed`) on every box with a known pull request: matched in its workspace [timeline](#timeline) by box
id, else by the box's branch against the PR's head branch. When several match, an open PR wins over a
merged or closed one, then the newest. `state` is the last GitHub sync's when this hub has one, else
the log's.

### Tasks

Units of work, ordered by priority (list order **is** the priority) and assigned to boxes. Many
tasks to one box is the normal case: that is how a manager keeps tasks touching the same files on
one branch. Assignments are healed on every read — a task assigned at create time moves from the job
id to the box id once the worker records it, and a task whose box is gone returns to the backlog
with its status untouched.

### Managers

A manager is a **host agent session** that creates and watches boxes — many per workspace, of three
kinds. `external` is a claude or codex session in someone's own terminal: the CLI registers it the
first time it runs inside it (`POST /managers/detect`), and the hub only observes it. `pty` is one a
hub started on an AgentBox pty host on its own machine — one process holding the agent's terminal,
with no multiplexer in between, so every client gets the agent's raw bytes and several can attach at
once. `tmux` is the same thing on the older carrier, used where the optional terminal prebuild is
missing. A running `pty` manager carries `ptyAttach` (an absolute argv, its socket and the protocol
version), so an embedding client needs nothing on its own PATH.

**A manager runs on one machine; its record lives with the workspace.** With a control box configured
those are different machines: the session, its tmux server and its transcript are on your PC, while
the record, its notes and its timeline are on the box. `host` is the machine it runs on and
`hostIsHub` says whether the hub that answered IS that machine. Every process op — start, resume,
attach, stop, sessions, message — only works there; anywhere else it answers `409` with code
`wrong_host` and `details.host`, and the client retries against the hub on that machine (its own
local hub, when `details.host` is its own hostname — `agentbox hub target --json --local` points at
it). The PC hub keeps that record current by reporting to `POST /managers/{id}/heartbeat`, and tells
it about a box it built for that manager with `POST /managers/{id}/attach-box`. Registering,
reporting and attaching a box are the only manager writes a hub accepts from another host.

`status` is derived, never stored: on the machine that runs it, whether the session host answers for
a `pty` manager, the tmux session for a `tmux` one, and for an `external` one its pid, else "seen in
the last 30 minutes". A claude session that
Claude Code hosts in its background daemon (`claude --bg`, listed by `claude agents`) is `running`
while the daemon runs it, whatever is attached. On any other hub the row comes from the last
heartbeat, and falls back to the last-seen window once three of them are missed. An external session
that has ended can be **resumed**, after which it is hub-run.

Claude's daemon hands the environment of the client that started it to every session it hosts, so a
detect's `managerId` (`$AGENTBOX_MANAGER`) is believed only for a manager in the same folder that has
no session yet or is hub-run and running. For a `pty` manager it is believed only when the detect
also carries `runId` (`$AGENTBOX_MANAGER_RUN`), which its session host minted — proof the leaked
variable cannot supply. A detect that names the AgentBox tmux session it runs in
(`tmuxSession`) records the manager as run from it, when that session exists on the hub's machine
and started in the detect's folder.

A manager: `{ id, workspaceId, workspaceName, agent, kind, host, hostIsHub, status, resumable, resumeBlockedBy?, cwd, sessionId?, title?,
pid?, pidStartedAt?, tmuxSession?, tmuxPane?, attachCommand?, boxIds, boxJobIds, taskCounts, createdAt, lastSeenAt, startedAt?,
stoppedAt?, lastExit?, background?, terminalSession? }`. `attachCommand` is present for a running hub-run manager, and for a
background session while the hub's attach session for it is up. `background` (`{ id, status?, state?, name? }`) marks a
claude session running detached in Claude's daemon — no AgentBox tmux session starts in its folder and no `claude attach`
client shows it — which `POST /managers/{id}/attach` opens. `terminalSession` names the one unclaimed AgentBox tmux
session that started in a running external manager's folder (for example one from before managers were detected): a
client may offer to open it, but nothing ties it to the manager for sure. `resumable` says whether a resume
would be accepted at all (a client disables Resume on `false`), and `resumeBlockedBy` says why not —
`running`, `no-session` or `unsupported-agent`, absent when `resumable` is true. It says nothing about
WHERE: that is `host`/`hostIsHub`. `title` is the session's first user turn when the machine running
it can read the agent's store.

### Timeline

What happened in a workspace, from an append-only log every mutation writes to — task, manager, box,
push and pull-request events — plus the rows that are true right now.

| Endpoint                                | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /workspaces/{id}/timeline`         | `{ items, live, summary?, github }`, items newest first. `?before=<iso>&limit=` (default 100, max 500) pages back; `?since=<iso>` adds `summary: { since, merged, additions, deletions, tasksDone, awaiting }` and does not filter the items. `?sync=0` skips starting the background GitHub PR sync (`github` reports the last one). `?managerId=` narrows `items`, `live` and `summary` to one manager session: the rows it stamped, plus the rows on a box it owns (most box, push and PR rows carry no `managerId` of their own). An unknown id reads as an empty timeline, not an error. |
| `POST /workspaces/{id}/timeline/events` | Record one event from a hub that does not hold the store. Body is an event without `id` (minted here); `actor` must be `box`, `hub` or `manager` — a human action is made through this hub's own routes, which stamp it from the session header. `201 { event }` on append, `200 { deduped: true }` when the event's `key` was already in the log, `404` for a workspace this hub does not have. `at` is honoured, so a late forward is ordered by when the thing happened.                                                                                                                   |

An event is `{ id, at, type, actor, managerId?, turn?, prompt?, boxId?, boxName?, agent?, branch?,
base?, projectId?, taskIds?, task?, pr?, text?, noteKind?, boxRunning?, additions?, deletions?, key? }`. `actor` is `human`,
`manager`, `box`, `hub` or `github`. `type` is one of `task.created | status | assigned | unassigned |
removed`, `manager.joined | started | resumed | stopped | note | message`, `box.created | ready |
failed | started | stopped | destroyed | branch`, `git.push`, and `pr.opened | ready | merged | closed`.
`base` on `box.created` is the branch the box forked from: the create's `fromBranch`, else the branch the
project's checkout was on (absent on a detached HEAD). `box.branch` is written when a
`git/checkout` or `git/branch` moves the box onto another branch, with `branch` the branch it is now on
and `base` the one it left; a checkout with `args` (paths) or one that leaves HEAD detached writes
none. `box.ready` carries `base` only when the create named a `fromBranch`. A
`git.push` carries `additions`/`deletions` from the old tip to the new one, or from the merge base
with the default branch for a first push. They are read from the host repo when the hub holds that
folder, and measured inside the box when it does not — a control box has no checkout of anything.
`taskIds` is captured when the event is written, and `pr` is `{ repo, number, title, url, base, head,
additions?, deletions?, checks?, mergeState?, autoMerge?, mergedBy? }`.

An item is an event, or `type: plan` (`count`, `taskIds`, `turn`, `prompt`) when a manager created 3 or
more tasks in one turn within 10 minutes. A `pr.merged` preceded by a message about that PR carries
`approvedByYou`. `live` rows are `task.in_progress` — a box working a task, with `filesChanged`,
`additions` and `deletions` of its uncommitted diff while it runs (left off a read when the box takes over
3 s to answer) — and `pr.ready`, with `awaiting` and, once a message about it was sent, `approved`.
After a hub restart, a ready PR stays out of `live` and `summary.awaiting` until a GitHub sync of the
workspace confirms it.

Items and `live` rows that name a branch carry `branchUrl`, the branch on the web
(`https://github.com/acme/storefront-web/tree/feat/checkout-copy`, each segment URL-encoded). A PR
row's branch is its `pr.head`. The repo comes from `pr.url`, else a repo the GitHub sync resolved, else
the row's project or box as the last sync cached it; without one of those the field is absent. A read
never runs `gh` for it, so a row can gain the link on the read after the first sync.

**Lanes.** Every item and `live` row carries `lane: { id, kind, from?, into?, branch?, open? }`, for
drawing the timeline as a branch graph. `id` is `box:<boxId>` for a box's rows (a `box.created`
joins its box through its create job), `branch:<head>` for a pull request no box is known to own, and
`trunk` for everything else: tasks without a box, managers, notes, plans. `from` is on a lane's
oldest row: the box lane that last carried its `base` (a PR lane uses `pr.base`), else `trunk`. `into`
is on `pr.merged`: the box lane carrying `pr.base`, else `trunk`; the row itself stays on its own
lane. `branch` is on a lane's first row and wherever its branch changes. `open` is on live rows and on
a lane's newest item when the lane goes on: its box has a live row, or still exists and is running or
has not merged its work. Lanes are assigned over the whole log before `before` and `limit` apply, so a
lane keeps its id on every page, and a page that does not reach a lane's fork has no `from` for it.

**Who did it.** The CLI sends `X-AgentBox-Session: <agent>:<sessionId>` from inside a Claude Code or
Codex session; the hub resolves it to a registered manager and stamps its `managerId`, `turn` and that
turn's `prompt`. Without the header (the tray, the web UI, a script) the actor is `human`, and so is a
manager of another workspace: on a box or manager route the session is resolved in that box's or
manager's own workspace. Alongside it the CLI sends `X-AgentBox-Session-Turn: <turn>[;<prompt>]` (the
prompt percent-encoded), read from the transcript on ITS machine — a control box holds the manager
record but not the transcript. It is used only when the resolved manager's session is on another
host; where the hub can read the transcript it does, and ignores the header. `note`
(up to 2000 characters) on a task add, update, assign or reorder body records a `manager.note` next to
the change.

**Pull requests** come from two places that share one dedupe key: the in-box `gh` shim after an
exit-0 `gh pr create` or `gh pr merge`, and a GitHub sync — `gh pr list` on the GitHub repos the
workspace's projects name — that a read starts in the background when the last one is over a minute
old. Every `gh` call it makes addresses the repo by name and runs in no folder, so a hub with no
checkout syncs exactly like one that has them; a project with no `repoUrl` has nothing to poll. It
keeps PRs on a branch the workspace worked on, or opened by the `gh` user. `github` is `ok`,
`syncing` or `unavailable` (no `gh`, not logged in, or no GitHub repo); rows a sync adds fire the
usual `/api/events` change.

### Custody

Custody holds agent credentials, `.env`/secret files, and **per-box SSH private keys** — the highest-value target in the whole API. It follows a **two-tier contract**: `list` / `PUT` / `DELETE` authorize with the hub API key and their responses are **metadata only** (paths, hashes, sizes, mtimes — never a value); the byte-read `GET /custody/{path}` is the only route that returns a value, and it is **elevated** — on a control box it additionally requires the admin token, so the widely-distributed API key alone can never read a secret.

| Method + path              | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /custody`             | Metadata of what the hub holds so a box created from either side is usable from both — agent credentials, project seeds, provider bake records, and per-box SSH keys: `{ enabled, entries: [{ path, size, sha256, mode, updatedAt }] }`. **Value bytes are never returned** (same contract as `agentbox hub custody list`). Optional `?prefix=` scopes to a custody scope (`agents` \| `projects` \| `prepared` \| `boxes`) or a `scope/subject` (e.g. `boxes/box-abc`); a malformed prefix is `400`. Drives the web UI's **Custody** page.                                                                                                                                                                       |
| `PUT /custody/{path}`      | Store bytes at a custody path (body `{ data: <base64> }`). Returns metadata only — `{ path, size, sha256, mode, updatedAt, changed }`, **never the stored value**; `changed: false` when the bytes were already there (content-addressed). Backs `agentbox hub credentials/secrets/project push`.                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `DELETE /custody/{path}`   | Remove one custody entry (`204`, or `404` if absent). Backs `agentbox hub custody rm`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `GET /custody/{path}`      | Read a stored blob's **bytes** (`{ …metadata, data: <base64> }`). **Elevated**: on a control box this additionally requires the admin token in `X-Agentbox-Admin-Token`; the hub API key alone can list and write but **never read a value** — a byte-read with only the API key is `401`. (A localhost hub needs no admin token — its hub token is a machine-local secret — but the byte-read is **loopback-only** there: the localhost hub binds `0.0.0.0` so containers can reach it, so a non-loopback byte-read is refused even with a valid token, because custody bytes must not leave the machine over the network.) Backs `agentbox hub credentials pull` / `custody pull` and per-box SSH-key adoption. |
| `PUT /custody/blob/{path}` | Stream bytes into a custody path (`application/octet-stream`). The **advanced** counterpart of `PUT /custody/{path}`: the JSON route stays the easy, general-purpose API for small values, while this one carries payloads where base64-in-JSON would cost several times the payload in peak memory on both ends — chiefly a project's `carry:` material, which can run to `box.cpMaxBytes` (100 MiB). Capped by `AGENTBOX_CUSTODY_MAX_BLOB_BYTES` and enforced mid-upload, so an over-cap body is cut off rather than landed. Returns metadata only, content-addressed like the JSON route.                                                                                                                      |
| `GET /custody/blob/{path}` | Stream a stored blob's **bytes** back (`application/octet-stream`, digest in `X-Agentbox-Sha256`). Same **elevated** gate as the JSON byte-read — streaming changes the transport, never the trust.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

### System

| Method + path | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /system` | "What is running here, and do I need to re-bake?": `{ hub, build, deploy, providers, hostCarried, boxImage }` — the hub version/channel/build source, the deploy record (when this machine is an exposed/deployed control box), each base provider's baked fingerprint + freshness (`baseStatus` `stale` = re-bake, with `baseStaleReason` and a `bakeDiff` naming the files that changed), the agent configs/skills this machine carries into a box, and the box-image registry + exact pull tag. Freshness is populated only on the in-process host topology (like `GET /providers?freshness=1`). Drives the web UI's **System & Build** page. |

The box view is provider-agnostic: `{ id, projectId, repo, branch, task, agent,
status, createdAt, lastActivity, host, commits, filesTouched, error, displayName,
webUrl, vncUrl }`, where `status` is one of
`running | paused | stopped | creating | error`. Boxes still being created (and
failed creates) appear as synthetic `creating`/`error` entries with a `job:` id
until the real box lands. A failed create can be cleared with
`POST /boxes/{id}/destroy` (dismiss). On the local host topology each box also carries raw
host-side fields for native clients (the tray app): `state` (the raw provider
state — absent on synthetic entries, which is how a client tells a failed create
from a running box whose agent errored), `name`, `provider`, `projectRoot`,
`projectIndex`, `vncEnabled`, `persistent` (an always-on box — never auto-paused,
never idle-lapsed, skipped by prune, restarted by the relay's boot reconcile; see
[persistent boxes](/docs/checkpoints-and-pausing#persistent-boxes). `POST /boxes/{id}/destroy`
has no guard on it, unlike `agentbox destroy -y`, so a client that offers destroy
should confirm on this field), `gitWorktrees`,
`shellCount`, and `agentStatus` —
every agent reporting in the box, keyed by agent id, each `{ state, sessionTitle? }`
where `state` is one of `working | idle | waiting | end-plan | question |
compacting | error | unknown`. The older named fields (`claudeSessionTitle`,
`codexSessionTitle`, `opencodeSessionTitle`, `claudeActivity`, `codexActivity`,
`opencodeActivity`) are still sent, but they are a projection of `agentStatus`
over the three built-in agents — read `agentStatus` if you want to see any
other agent. `vncEnabled` — not `vncUrl` — is the
"this box has a desktop" bit: `vncUrl` is only ever set for boxes with a stable
URL (docker, hetzner), and is `null` on daytona/vercel/e2b because their signed
preview URLs expire. Gate the affordance on `vncEnabled` and fetch the URL from
`GET /boxes/{id}/vnc` when the user clicks. Cloud boxes also carry the fields
needed to reconstruct or adopt them from the payload alone (all `undefined` for
docker/synthetic rows): `sandboxId`, `originUrl`, `publicHost`, `image`,
`webPort`, `previewUrls`, `lastAgent`, and `topology`.

## Creating a box

Creation is asynchronous — it enqueues a build job and returns immediately:

```bash
# Register the folder once (skip if it's already a project):
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"path":"/abs/path/to/repo"}' \
  http://127.0.0.1:8787/api/v1/projects

# Create a box for it (grab the projectId from GET /projects):
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"projectId":"<id>","agent":"claude","name":"feature-x"}' \
  http://127.0.0.1:8787/api/v1/boxes
# -> 202 { "jobId": "..." }
```

The body takes **either** a `projectId` (a registered project on the hub's
machine — built from its local checkout) **or** a `repoUrl` (an origin the hub
clones VPS-side when there is no local checkout, e.g. on a control box). Same
route, same `202 { jobId }` — the hub picks the build path internally. Optional
fields mirror the CLI's `agentbox create` flags: `agent`, `provider`, `name`,
`prompt`, `agentArgs`, `fromBranch`, and an `opts` object for box-shaping knobs
(`image`, `snapshot`, `size`, `location`, `envFiles`, `carry`, …).

### Questions a create has to ask first

Some creates need a human decision before anything is provisioned: whether to
copy the host files a project's [`carry:`](/docs/agentbox-yaml#carry) block
names, or whether to seed a service agent with a host login. `POST
/projects/{id}/create-preflight` returns those questions; you render them, and
send the answers back with the create.

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"agent":"claude","provider":"docker"}' \
  http://127.0.0.1:8787/api/v1/projects/<id>/create-preflight
# -> { "prompts": [ { "id": "carry:98310458c334", "topic": "carry", "kind": "select",
#                     "title": "Copy 15 host entries into the box?",
#                     "choices": [ ... ], "detail": { "type": "file-table", ... },
#                     "required": true, "fallback": { "value": "cancel", ... } } ],
#      "unavailable": [] }

curl -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"projectId":"<id>","agent":"claude","opts":{"promptAnswers":[
        {"id":"carry:98310458c334","value":"approve"}]}}' \
  http://127.0.0.1:8787/api/v1/boxes
```

Once a project's `carry:` list is approved it stops being asked at all — the approval is remembered host-side (see [carry](/docs/agentbox-yaml#carry)), so the preflight returns no `carry` prompt until the list changes. Send `carryAsk: true` to show it again for a granted list; answering **Skip** or **Cancel** on the create that follows withdraws the standing approval.

A client that already holds the answer can skip the two-step conversation and post the **decision** instead of an answer list: `opts.carryYes` approves the block, `opts.carrySkip` declines it. Both are per-run and leave no standing grant, which makes them the API twins of the CLI's `--carry-yes` and `--carry skip` — and the way a scripted create gets through with no terminal to prompt at.

A `PromptRequest` has two halves. The generic one — `kind` (`confirm` /
`select` / `text`), `title`, `body`, `choices` — is enough to render and answer
**any** prompt, including a `topic` your client has never seen, so the hub can
add a question without breaking you. `detail` is the optional half a client
_may_ draw richly (`file-table`, `credential`); every variant carries a plain
`summary`, so render that for one you do not recognise.

The list comes from running the real gates, so it can never differ from what the
create asks. Skipping the endpoint is allowed — every prompt has a `fallback` —
except for one marked `required` (`carry:`, whose silent answer would move host
secrets): a create that leaves that unanswered is refused, not defaulted. Ids
are content-addressed over the question, so an answer collected before the
project's `agentbox.yaml` changed no longer matches and is refused too.

`unavailable` names each gate this hub cannot run and why. A control box has no
local checkout, so it can read neither your `agentbox.yaml` nor your host
logins; it says so rather than returning an empty list that looks like "nothing
to ask".

A box being built shows up in `GET /boxes` with `status: "creating"` right away,
then flips to `running` once the container is up. `GET /jobs` lists every
create job (the unified queue view behind `agentbox queue list` / `hub jobs`);
`GET /jobs/{id}` is one job's status (`queued`/`running`/`done`/`failed`, plus
`boxId` and, on failure, `error`).

## Streaming logs (SSE)

`GET /jobs/{id}/logs` is a Server-Sent Events stream: an `open` event, then a `log`
event per line, then a terminal `end` event with the final status.

```bash
curl -N -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8787/api/v1/jobs/<jobId>/logs
```

```
event: open
data: {"id":"<jobId>"}

event: log
data: "... building image ..."

event: end
data: {"status":"done"}
```

## Installing providers &amp; baking images

Before a cloud provider can host boxes it needs two things on the host: its
**credentials** and its **baked base image**. Both are drivable over the API
(the hub settings UI uses exactly these calls), so you never have to drop to a
terminal:

```bash
# 1. Save credentials (validated against the cloud, then written to secrets.env):
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"apiKey":"e2b_..."}' \
  http://127.0.0.1:8787/api/v1/providers/e2b/credentials
# -> 200 { "ok": true }   (a rejected token -> 400 with the reason)

# 2. Bake the base image (async — stream the build like a create job):
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{}' http://127.0.0.1:8787/api/v1/providers/e2b/prepare
# -> 202 { "jobId": "..." }
curl -N -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8787/api/v1/jobs/<jobId>/logs
```

Once the bake finishes, `GET /providers` reports the provider as `configured:
true` and it becomes a valid `provider` for `POST /boxes`. Docker needs no
credentials; its base self-heals, so a bake there is optional (a `force` rebuild).

<Callout type="info" title="Host capability">
  These two endpoints run on the host that owns Docker/SSH and writes `~/.agentbox` — the local or
  full-host hub. On the hosted (serverless) plane they return `503`.
</Callout>
