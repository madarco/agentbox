AgentBox ships a handful of Claude Code skills (mirrored as Codex prompts and OpenCode commands) so the agent itself can drive AgentBox. One forks your current session into a new box, one teaches the agent to operate the `agentbox` CLI on your host, and one runs _inside_ a box to configure it. The npm package installs them for you.

<Callout title="NOTE">
  These are the AgentBox-provided skills, not the same thing as your own `~/.claude` skills — though
  those flow into every box too (see [Keeping boxes in sync](#keeping-boxes-in-sync)), and the hub
  keeps a library of them across your PCs (see [Your skills library on the
  hub](#your-skills-library-on-the-hub)). For the agent session itself, see [Run an
  agent](/docs/run-an-agent).
</Callout>

## Install the skills

The skills come with the npm package. The first-run `agentbox install` wizard installs them as its last step; re-run it (or the `--skills-only` shortcut) any time to refresh them.

```bash
npm -g install @madarco/agentbox
agentbox install                  # full wizard; installs the host skills as its last step
agentbox install --skills-only    # just (re)install the host skills
```

They land in `~/.claude/skills/agentbox/` and `~/.claude/skills/agentbox-info/`, with mirrors at `~/.codex/prompts/agentbox.md` and `~/.config/opencode/commands/agentbox.md`. The installer is idempotent and only touches files it wrote — pass `--force` to overwrite a copy you've hand-edited. See [CLI commands](/docs/cli) for the rest of the `install` flags.

## `/agentbox` — fork a session

`/agentbox [provider]` is the user-invokable slash command. Run it from Claude Code or Codex and it teleports your _current_ session — the full conversation, plus the active plan if you're in plan mode — into a fresh box and resumes it there. The provider argument is optional and defaults to local Docker.

<Callout type="warn" title="OpenCode">
  OpenCode sessions can't be teleported yet — its sessions live in a multi-tenant SQLite database,
  and per-project extraction is tracked as a follow-up. The command is installed for OpenCode but
  refuses with that explanation; run `agentbox opencode` to start a fresh session in a box instead.
</Callout>

```text
/agentbox            # fork this session into a local Docker box
/agentbox hetzner    # fork into a Hetzner cloud box
```

Under the hood it calls `agentbox fork`. It's host-only in v1 (forking from inside a box isn't supported yet). The full flag reference — `--agent`, `--name`, `--plan`, and the rest — lives in [CLI commands](/docs/cli).

## `agentbox-info` — operate AgentBox from chat

`agentbox-info` is a host-side _reference_ skill. Claude loads it automatically — there's nothing to type — when you ask it to spin up boxes, queue background runs with `-i`, or push commits safely through the host relay. It's the knowledge that lets an agent already running on your laptop operate the `agentbox` CLI on your behalf.

<Callout title="TIP">
  You never invoke `agentbox-info` directly; it's auto-loaded by relevance. Just ask your host agent
  to "start a box" or "queue three runs" and it knows the commands. See [Orchestration & queue
  boxes](/docs/background-and-parallel).
</Callout>

## `agentbox-setup` — configure a box from the inside

`agentbox-setup` runs _inside_ a box. When the agent in a box has no [`agentbox.yaml`](/docs/agentbox-yaml) — or you ask it to (re)configure one — this skill walks it through discovering the project's services and tasks and writing `/workspace/agentbox.yaml`, so the in-box supervisor can boot the workspace deterministically.

It ships in the box image rather than in your host `~/.claude`, so it's only active where it's useful. See [Services & tasks](/docs/services-and-tasks) for the file it produces and how the supervisor runs it.

## Keeping boxes in sync

Your host `~/.claude` is the source of truth. Every `agentbox create` / `agentbox claude` syncs it into the next box, so your skills, plugins, MCP servers, and login all flow in automatically. A running box doesn't resync on a plain `attach` — use `agentbox claude start` after you install a new skill or sign in on the host, and it picks up the change.

<Callout type="warn" title="HEADS UP">
  `attach` never resyncs your host `~/.claude`. After installing a skill or signing in on the host,
  use `agentbox claude start` (or a fresh `agentbox claude`) so the box picks it up.
</Callout>

## Your skills library on the hub

The hub keeps a library of your own skills, so the same set is available from every PC that uses it, local hub or [deployed control box](/docs/deployed-hub) alike. Skills are stored in the hub's custody (the `skills` scope), one tarball per version, identified by a hash of the skill's files.

**First time: automatic.** The first time a hub has never held a skill, AgentBox seeds it from the PC you are on: at the end of `agentbox hub setup` / `hub deploy`, or on your first `agentbox create` / `agentbox claude` against that hub. It uploads every skill in `~/.agents/skills` and the agents' own skill folders (`~/.claude/skills`, `~/.codex/skills`, `~/.config/opencode/skills`, `~/.pi/agent/skills`, `~/.openclaw/skills`), one copy per name, and prints one summary line. It never seeds AgentBox's own skills (`agentbox`, `agentbox-*`) or Claude Code's claude.ai-synced skills (`~/.claude/skills/synced/`).

**After that: explicit.** The automatic seed runs once per hub, even if you later discard every skill. New skills reach the hub only when you upload them.

```bash
agentbox skills                          # interactive: local vs hub side by side, then upload / download / discard
agentbox skills --list                   # the same table, non-interactive (--json for scripts)
agentbox skills --upload unslop,daytona  # upload these local skills
agentbox skills --upload-all             # every local skill the hub lacks or has differently
agentbox skills --download-all           # bring this PC in line with the hub
agentbox skills --download inngest       # into ~/.agents/skills/inngest (+ a ~/.claude/skills link)
agentbox skills --discard old-skill --yes
```

The table compares each skill by content: `same`, `differs` (with which side changed last), `local only`, or `hub only`, with the size, the PC it came from, and when it was updated.

- **Download** writes to `~/.agents/skills/<name>`, which Codex, OpenCode, Pi and OpenClaw read, and links `~/.claude/skills/<name>` to it for Claude Code. A local copy with different content is replaced only after you confirm (or with `--yes`). The downloaded files are checked against the version hash before anything is written.
- **Discard** deletes the skill and every stored version from the hub. It asks first; off a terminal it needs `--yes`.
- **Upload** keeps the hub's older versions (the newest 5 per skill).

<Callout type="warn" title="SECRET SCAN">
  Before a skill leaves your PC it is scanned for credentials: private keys, cloud and LLM API keys,
  tokens, `KEY=value` / `key: value` lines naming a secret, passwords inside URLs, and files whose
  name says they hold credentials (`.env*`, `*.pem`, `*.key`, `id_*` private keys, `.netrc`,
  `.npmrc`, `.pypirc`, `credentials*.json`; `.env.example`-style templates excepted). Documentation
  placeholders such as `YOUR_API_KEY`, git hashes and test fixtures are ignored. A flagged skill is
  skipped by the automatic seed and named in its summary; upload it from `agentbox skills` after
  reviewing the finding, or with `--allow-findings`. Findings name the file and line, never the
  value.
</Callout>

A skill must have a `SKILL.md` whose frontmatter `name` matches its folder and carries a `description`; a skill with a broken symlink, or bigger than [`skills.maxSkillBytes`](/docs/configuration#skills) (50 MB), is listed and skipped. A skill that holds a symlink pointing **outside its own folder** (for example `refs -> ~/Projects/app`) is skipped too, with the link named: following it would upload that whole folder, `.env` files included.

**In the hub web UI**, the **Skills** page lists what the library holds (description, size, file count, the PC it came from, when it was updated, how many versions are kept) and manages it without a terminal. See [The Skills page](#the-skills-page). Uploading from and downloading to a PC's folders stays with `agentbox skills` on that PC, since only it can read and write them.

### Library skills in boxes

A box created against a hub that holds a library pulls its skills when it starts: its in-box supervisor asks the hub for the box's set over the same channel it uses for everything else, downloads each skill, checks it against its version hash, and keeps it in the box (`~/.local/share/agentbox/skills`). This works the same on every provider, Docker and cloud, including a box created on a control box whose own machine has no skills. Every agent sees them in its own way, without any setup:

| Agent       | How the library reaches it                                               |
| ----------- | ------------------------------------------------------------------------ |
| Claude Code | linked into its managed skills folder, `/etc/claude-code/.claude/skills` |
| Codex       | linked into `/etc/codex/skills` (Codex's admin scope)                    |
| OpenCode    | linked into `~/.opencode/skills` (your own `skills.paths` still loads)   |
| Pi          | launched with `--skill <folder>`                                         |
| OpenClaw    | the folder is added to `skills.load.extraDirs` at boot (picked up live)  |

Skill names are unchanged in every agent (`/unslop`, and `skill:unslop` in Pi as for any Pi skill). If a skill with the same name also arrives from your machine's `~/.agents/skills` (see below), OpenCode uses the library copy, Codex lists both, and Pi and OpenClaw use the copy from your machine.

Pick a box's skills when you create it:

```bash
agentbox claude --skills unslop,frontend-design   # only these
agentbox claude --skip-skills daytona             # all but these
agentbox create --no-skills                       # none
```

Without a flag a box gets every library skill. The choice is recorded on the box and applies again when it restarts; a restart also picks up the library's newest versions and drops skills removed from it. Running boxes are updated too (see [Sources and updates](#sources-and-updates)); `agentbox skills update --box <box>` syncs one now, as does `agentbox-ctl skills sync` inside it.

#### Bindings: per workspace and per project

The hub also keeps **skill bindings**, which turn a library skill on or off for every box of a workspace or a project, on whichever PC or provider the box is created:

```bash
agentbox skills disable daytona                       # leave it out of the library set for every box
agentbox skills enable daytona --workspace            # ...but on in the workspace of this folder
agentbox skills disable unslop --project              # off for this folder's repo
agentbox skills enable unslop --project https://github.com/acme/app
agentbox skills enable daytona --workspace --clear    # remove that binding again
agentbox skills bindings [--json]                     # list every binding
```

For each skill the most specific choice wins: a binding for that one box (made through the API, or by approving an agent's install request, see below), then the create flags above, then the project, then the workspace, then a global binding. A skill bound nowhere is in every box. `--project` with no value uses this folder's `origin` remote; a project is keyed by its repo, not a folder, so the same repo checked out on two PCs gets the same set. `--workspace` with no value uses the [workspace](/docs/cli#workspaces--tasks) containing this folder, or takes its id or name. Enabling a skill for one workspace or project only narrows anything if it is disabled globally; the command says so when it isn't.

Bindings select what boxes receive **from the library**. A skill that also arrives from your machine's own folders (see [Keeping boxes in sync](#keeping-boxes-in-sync)), such as a copy in `~/.claude/skills` or `~/.agents/skills` on Docker, or one baked into a cloud base, still reaches the box that way, so disabling it in the library doesn't remove that copy.

In the hub web UI, the create form's **Advanced** section lists the library skills ticked as the bindings resolve for the chosen project. Leave it alone and the bindings decide. Unticking a skill skips just that one; ticking one the bindings leave out gives the box exactly the ticked set.

A running box applies binding changes when it restarts or on `agentbox-ctl skills sync`.

If the hub has no library, or can't be reached, nothing changes: boxes keep receiving your skills from your machine as described in [Keeping boxes in sync](#keeping-boxes-in-sync). Delivery needs a box image from this version or later; an older Docker image or cloud base keeps the old behaviour until it is rebuilt (`agentbox prepare`).

Downloading a skill's files from the hub (`agentbox skills --download` / `--download-all`) is treated like reading custody, so it needs more than the API key the menu-bar app and web UI hold: the admin token, a computer enrolled with [`agentbox hub login`](/docs/deployed-hub), or, on a local hub, a request from the same machine. A computer that only holds the hub's API key (configured with `agentbox hub set-url` and `AGENTBOX_HUB_API_KEY`) can still list the library, but a download is refused (`401`); enroll it with `agentbox hub login` instead. In the hub web UI, the owner signed in on a deployed hub may read a skill's content (its update diff and `SKILL.md`); the API key alone still can't. Boxes are unaffected: they fetch their skills over the relay, authenticated as the box.

### Sources and updates

Besides uploads from a PC, the library takes skills from a git repo or a Claude Code plugin marketplace. The **hub** fetches them, so this works the same against a deployed control box, and each skill goes through the same checks as an upload (frontmatter, size cap, secret scan).

```bash
agentbox skills add owner/repo                         # every skill in skills/<name>/ or <name>/ (a picker on a terminal)
agentbox skills add https://github.com/o/r.git#skills/foo@v1.2   # one folder, at a tag
agentbox skills add owner/repo --skill alpha,beta      # only these
agentbox skills add --marketplace claude-plugins-official --plugin some-plugin   # only that plugin's skills
agentbox skills import ~/work/my-skill --link          # upload a folder and keep it in sync
```

A marketplace name is looked up in this PC's `~/.claude/plugins/known_marketplaces.json`; pass its git URL or `owner/repo` instead to name it from anywhere. Plugins themselves are not imported, only their skills.

**Update policy.** Each skill has one:

- `auto` (the default for uploads and linked folders): a new version becomes current right away, and every running box that holds the skill syncs it within seconds. Paused and stopped boxes catch up when they start.
- `manual` (the default for git and marketplace skills): a new version is fetched and stored but waits as **pending**. Boxes keep the version they have until you approve it.

```bash
agentbox skills refresh                 # re-fetch every git/marketplace skill
agentbox skills --list                  # STATUS shows "update pending"
agentbox skills diff some-skill         # what the pending version changes, file by file
agentbox skills update some-skill       # shows the diff, asks, then applies it and syncs boxes
agentbox skills update --all --yes      # apply every pending update without asking
agentbox skills policy some-skill auto  # or switch a skill's policy
```

A force-pushed branch shows up as a new pending version like any other commit; nothing third-party changes in a box without an approval.

**Linked folders** are for writing a skill: `agentbox skills import <path> --link` uploads the folder and records it in `~/.agentbox/skill-links.json`. From then on this PC's relay (or local hub) watches the folder and uploads a new version a moment after each save, and running boxes pick it up. `agentbox skills unlink <name>` stops watching; the hub keeps the skill.

**What a box holds.** `agentbox skills ls --box <box>` lists the library skills a box was last given, and marks each one `behind` when the box holds an older version than the library's (for example a box that was paused through an update). An updated skill is active from the agent's next session: Codex, OpenCode and Pi read their skills when a session starts, OpenClaw reloads them on its own.

### Skills written in a box

When an agent writes a new skill inside a box (say `~/.claude/skills/release-notes/`), it can join the library so later boxes get it too. `agentbox download <agent> [box]` (claude, codex, opencode, pi, openclaw) also reads the agent's skill folder in the box and **proposes** each skill the library doesn't hold (at any kept version) and this PC didn't already have as-is before the pull:

```bash
agentbox download claude mybox
#   release-notes: proposed as a new library skill
# 1 skill proposal(s) wait for approval in the hub (web Approvals, the tray, or a box footer); approved skills reach new boxes.
agentbox download claude mybox --no-propose   # skip the proposal step
```

Each proposal is one approval in the hub's approvals list (the web UI, the menu-bar app, an attached box footer), and the default answer is no. It is always asked of a person: a box with [`box.autoApproveHostActions`](/docs/configuration) does not approve its own proposals or installs. The approval lists every file added, modified or removed against the library's current version, with a diff of `SKILL.md`, so a changed script under an unchanged `SKILL.md` shows. The hub checks the skill itself before asking: the frontmatter `name` must match the folder and a description must be there, `agentbox-*` names are refused, and the secret scan runs, with its findings shown in the approval. Nothing is stored until you approve; then the skill is a new library skill (or a new version of one), current right away even under a `manual` policy, and running boxes that hold it sync it. A skill tracked from a git repo or a marketplace is never proposed over: change it upstream, or discard it from the library first. An unanswered proposal expires after a day. Symlinked entries (skills carried in from your machine) are never proposed. A waiting proposal is held in the hub's memory, so it is capped: at most 3 waiting per box and 10 on the hub, 8 MiB per skill, and 64 MiB for all waiting proposals together. Over a cap the proposal is refused with a message saying which one; answer the waiting ones and download again. The CLI checks a skill inside the box before copying it out, and again on what arrives: one over 8 MiB, or one holding a FIFO or device file, is skipped with the reason, and a `SKILL.md` that is not a regular file inside the skill is never read. An agent in a Docker box can start the same step itself with `agentbox-ctl download claude`, which asks you to allow the download first.

### Library skills for agents (MCP)

The `agentbox` MCP server every box registers (see [past sessions for agents](/docs/cli#past-sessions-for-agents-mcp)) also exposes the library:

| Tool                     | What it does                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| `skills_list`            | The library skills this box may use (`q` filters), each with `installed`.                    |
| `skill_get`              | One skill's `SKILL.md` and file list; `path` reads another file of it.                       |
| `skills_propose_install` | Ask for a skill this box was created without. One approval; then `agentbox-ctl skills sync`. |

A box sees only the skills its bindings allow (global, workspace, project and box bindings); a skill disabled for its project is invisible to it. An approved install is recorded as a binding for that box, so it outlasts restarts. Outside a box, `POST /api/mcp` with the hub credential lists the whole library; `skill_get` there needs the same access as downloading a skill (the admin token, an enrolled computer's token, or the same machine on a local hub), so the hub API key alone can list skills but not read them.

### The Skills page

The hub web UI's **Skills** page covers everything above that doesn't need a PC's folders:

- **Add from git** and **Add from marketplace**: enter a repository (`owner/repo` or a URL, with an optional path and ref), or a marketplace repository and a plugin name. **Look up** lists the skills the source holds, each with its size, any problem that would stop the import, and its secret-scan findings. Tick the ones to add, choose whether their updates wait for approval (the default) or apply automatically, and add them. A skill with findings is added only after you tick "I read the scan findings; add anyway".
- Each row shows where the skill comes from (upload, linked folder, git, marketplace) and its **update policy** (auto-update or approve updates), which you can switch in place.
- **Refresh** on a git or marketplace skill fetches its source again; **refresh all** does every one. A new version that the policy holds shows as **update waiting**. If the secret scan flags the new version, the refresh is stopped and **Fetch anyway** stores it after all, still waiting for approval.
- **Review update** opens the pending version: every file added, removed or modified against the current one, with a line diff of each text file, and the hub's secret scan of the new version. **Approve update** makes it current, and every running box that holds the skill syncs it.
- **Edit** opens the skill's `SKILL.md` in an editor; **New skill** starts one from a template. Saving stores a new version (the skill's other files are kept as they are), which becomes current and reaches running boxes like an upload. The frontmatter `name` must match the skill and a `description` must be there; a secret-scan hit stops the save until you choose **Save anyway**. Editing a git or marketplace skill turns it into an upload, so a refresh no longer fetches it, and the next save in a linked folder replaces an edit made here.
- **Skill proposals from boxes** (see [Skills written in a box](#skills-written-in-a-box)) are listed at the top of the page with Approve and Deny, next to the same entries in **Approvals**.
- **Discard** deletes a skill and its versions after a confirm.

Reading a skill's content (the update diff and the editor) takes the same access as downloading a skill. On a local hub, open the web UI from the same machine; on a [deployed control box](/docs/deployed-hub) sign in as the owner, and the diff and the editor work. The hub API key alone (what the menu-bar app holds) still can't read skill content.

Each **box's page** has a **Skills** section: the library skills the box was last given, with their versions and a `behind` mark when the box holds an older version than the library's; **Sync now** (a running box pulls its set at once); and an on / off / inherit choice per library skill for that box alone. That choice is a box binding, so it outranks the create flags and the project, workspace and global bindings; sync the box (or restart it) to apply it.

### Cloud bases go stale when your skills change

A cloud base (Hetzner, DigitalOcean, Daytona, Vercel, E2B) is baked with the skills on the machine that baked it, and the bake now records a digest of those skills (the ones the library would hold: valid, no secret-scan finding). When your skills change, that machine reports the base **stale** ("host skills changed since this base was baked"): `agentbox prepare --provider <id>` re-bakes instead of skipping, and the hub's **System** page shows the base as stale. If you have no skills, or the base was baked before this existed or on another machine, nothing changes. Docker and remote-docker boxes are unaffected; they receive skills when each box is created.
