# Remote control box — backlog

Host-local assumptions in the 0.31.x features that break or degrade when the hub is a remote control
box (`relay.controlPlaneUrl` configured). Found by the 2026-09-15 audit that produced
[`workspaces-remote-hub-plan.md`](./workspaces-remote-hub-plan.md); that plan covers only the 0.32
workspace layer and deliberately leaves these alone. Each item is documented, not fixed. Size:
S < half a day, M ≈ a day.

| 1 | `--model-auth` on a hub-routed create | The flag is never sent: `_cloud-agent-via-hub.ts` and `create.ts` `runCreateViaHubApi` have no `borrowCredentials` parameter although the wire field exists (`validate.ts`, `openapi.ts`). Set from the web UI, the hub resolves the source against ITS `~/.claude`/`~/.codex`/`process.env` (`create-gates.ts` → `borrowed-credentials.ts` → `resolveHostCredentialFile`), fails non-fatally, and the box boots with no model auth. | `apps/cli/src/commands/_cloud-agent-via-hub.ts`, `apps/cli/src/commands/create.ts`, `apps/hub/lib/prompts/create-gates.ts`, `packages/sandbox-core/src/borrowed-credentials.ts` | M |

| 13 | A manager's `boxJobIds` never promote to `boxIds` when the job is the PC's | The grouping lands (the enqueue sends `attachBox({boxJobId})`), but the promotion is `reconcileManagers`, which heals against the RECONCILING hub's own job list — the control box has no record of a `hub.mode=local` job, so it never promotes, and `manager list` counts the create as a pending job forever. The travelling patch is only ever called with `{boxJobId}`, never with `{boxId}` at completion, and the route takes "exactly one of the two ids" so it cannot express a swap. Decide which hub owns the promotion (the PC, at `completeCreateJob`, is the only one that knows) and let the attach carry both ids. Seen live: §F row F17, 2026-09-18. | `packages/relay/src/workspaces/manager.ts` (`reconcileManagers`), `apps/hub/lib/hub-backend.ts` (the `hub.create` wrapper), `apps/hub/app/(dashboard)/api/v1/managers/[id]/attach-box/route.ts` | M |
| 14 | A relay-executed `git.push` row carries no dedupe key | `recordBoxPushed` keys its row on the pushed tip (`push:<box>:<after>`), but that is the LEASED path only, and a control box in the default `gh` git-auth mode deliberately does not lease — the box routes through `recordBoxGitPush`, which passes no key. A second `agentbox-ctl git push` that prints `Everything up-to-date` therefore adds a second identical row. Either key the executor's row on the resulting tip too, or skip the row when nothing moved. Seen live: §F row F14, 2026-09-18. | `packages/relay/src/timeline-hooks.ts` (`recordBoxGitPush`), `packages/relay/src/host-actions.ts` | S |

| 15 | A docker box built under `hub.mode=local` is INVISIBLE to `list`/`ls` | **Won't fix — a consequence of an unsupported combination (2026-09-19).** `hub.mode` governs *gating* but not *targeting*. `dockerProvidersHidden` consults it, so `create` stops refusing and builds on the local hub (`withHubClient({preferLocal:true})`) — but `fetchBoxListing` resolves ONE target via `resolveHubTarget`, which never consults `hub.mode`, so the listing is fetched from the control box, which has never heard of the box. | ~~19~~ | ~~**An in-box agent can push any branch with no approval** (security)~~ | **Closed by a model change** (2026-09-19), not by the fix it first got. The original report was correct *under the model of the day*: approval was keyed on the host-registered branch alone while the box's argv tail was appended to `git push <remote> <branch>`, so from a box on `agentbox/g1-2` both `agentbox-ctl git push g11-plain-branch` and `agentbox-ctl git push HEAD:refs/heads/g11-injected` reached GitHub with `hub approvals list` -> "No pending approvals" and `/admin/prompts?all=1` -> `{"prompts":[]}` — an argv hole in a branch-shaped gate. `82cceadd` closed that hole by requiring every ref the assembled command would write to be an already-sanctioned target. Then the model itself changed by decision: publishing commits is ordinary, revertable agent work (the same reasoning that keeps `gh pr merge` off `GH_DESTRUCTIVE`), so **a push to any branch now runs silently and "which branch" no longer gates anything**. What gates today is what a push *does*: a deletion (`--delete`/`-d`, `:branch`), a force-push to a branch that is not the box's own `agentbox/*` scratch branch (`--force`/`-f`, a `+` refspec), `--mirror`/`--prune`, a tag overwrite, `--repo`/`--receive-pack`/`--exec`, and any flag the gate does not recognise (fail closed). `--force-with-lease`/`--force-if-includes` stay silent. `pushDestructiveReason` (`packages/core/src/sync/git-refs.ts`) is the one decision both gate sites read; `git.lease-token` keeps its own scratch-only gate because the credential it hands out bypasses this one entirely. | `packages/relay/src/server.ts` (docker path), `packages/relay/src/host-actions.ts` (cloud path), `packages/core/src/sync/git-refs.ts` | M |
| 20 | A control box IGNORES a pushed `prepared/<provider>.json`, so the first cloud create fails | With the bake record pushed (`hub custody list` -> `prepared/e2b.json`, present on the VPS at `hub-data/hub/custody/prepared/e2b.json`), the E2B credential present (`/api/v1/providers` -> `hasCredentials: true`) and the template live on the account, the control box still reports `configured: false` / *"Credentials set — bake the base image to finish setup"*, and a hub-routed create dies at `no E2B base template found` after provisioning. Almost certainly the build-context fingerprint (`contextSha256`): the VPS's own tree fingerprints differently from the PC's, so the pushed record is "not for this build context" — the same wording `hub expose` prints ("neither side has a e2b base for this build context"). Remedy today is a bake ON the control box, which then reports `[build] Template created with ID: o05kawibx9vcmxvgjnk4` — **the same id the pushed record already named**, i.e. the artifact was never missing, only the record of it. Live 2026-09-18 (§G row G12a). | the prepared-state resolution behind `/api/v1/providers` + the create worker's base lookup; `packages/sandbox-core` prepared-state | M |

Nothing new was found in Phase 4: the two enrichment paths it changed (PR sync, push +/-) were the
last host-checkout assumptions in the workspace layer, and item 12 was its own last open item.
Items 13 and 14 came out of the §F run against a real control box (2026-09-18); two other findings
from that run were fixed on the spot (a local hub inheriting the control box's auth profile, and a

Works remote as designed, no action: create-preflight's explicit `unavailable` (item 9 aside),
`agentbox url` / `agentbox-ctl open` / `GET /boxes/{id}/web`, the box size picker, `agentbox clone`
routing, `manager attach`'s refusal.

## §G general regression pass (2026-09-18, real Hetzner control box at `116.203.220.73.sslip.io`)

Items **15-20** above came out of it. It also **live-verified items 1, 2, 3, 8 and 14** (each had been
documented but not confirmed against a two-machine deployment) and **corrected items 4 and 5**.

What was confirmed WORKING remote, with a real control box and no laptop hub:
`create` (docker, via `hub.mode=local` — a shape that is no longer supported, see items 15 and 3) · lifecycle stop/start/pause/unpause · `status` ·
`checkpoint create/ls` · `url` + `GET /boxes/{id}/web` (resolves on the PC, 404 on the VPS, correctly) ·
`upload`/`download` (correctly NOT refused for a docker box — `remoteHubHostFileRefusal` keys on
`onThisMachine`) · `cp` both directions · `shell` · `--persistent` incl. the destroy guard ·
`hub credentials push` + `custody list` · `hub project push` · a hub-routed e2b create whose agent answers a
real prompt · **`agentbox-ctl git push` from a cloud box with the PC's hub AND relay stopped** (the whole point
of a control box) · the tray-facing payloads on `/api/v1/boxes`, `/api/v1/managers` (`hostIsHub: false` correct
across two machines) and `…/timeline` (`lane` + `branchUrl` on every row; `summary` only with `?since=`, by design).

**No regression attributable to `wip/remote-hub-p2-4` was found.** Every failure traced to a commit already on
`nightly`; the branch does not touch `git.ts`, `list.ts`, `hub-list.ts` or `remote-hub.ts` at all, and its edits
next to the push gate only extract `decideHostInitiatedPush` without changing how the bypass is computed.
